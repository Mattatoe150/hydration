# Production audit — 2026-08-20

Scope: the public site, GitHub repository, Cloudflare Pages project and Functions,
the production D1 database, and the daily OpenStreetMap refresh.

## Baseline verified

- `https://ikhebdorst.be` returned HTTP 200 and the English and Dutch map controls
  rendered successfully.
- The live map contained roughly 10,000 OpenStreetMap points plus the separate
  community feed.
- D1 was reachable and small (about 33 KB), with 19 approved additions and three
  accepted reports at audit time.
- A full production D1 export was taken before any database-changing work and
  stored outside the repository.
- Cloudflare Pages production deploys are explicit uploads associated with the
  `main` commit. A verified preview was promoted after the pull request merged.

## High-priority findings fixed

1. The daily refresh required `tools/i18n_nl.json`, but the ignore rule excluded
   that file from Git. A clean runner would fail before it could rebuild the Dutch
   page. The translation source is now tracked and tested.
2. The refresh workflow only committed `index.html`; `nl/index.html` and the
   sitemap could drift. All three generated artifacts are now verified and
   committed together.
3. Untrusted OpenStreetMap labels were inserted directly into an inline script.
   A label containing `</script>` could escape the data block. Inline JSON is now
   encoded for HTML script context and covered by a hostile-input regression test.
4. Pending contributor names and moderation notes were returned by the public
   suggestions feed. Pending names are now masked and moderation-only fields are
   omitted.
5. The public POST body was unbounded and its rate-limit check could race with a
   simultaneous insert. Bodies are bounded, kinds are explicitly validated, and
   rate checking plus insertion now happen in one D1 statement.
6. A public fallback IP-hash salt weakened pseudonymisation. Submissions now fail
   closed if the private salt or Cloudflare caller address is unavailable.
7. The production schema and repository schema had drifted (`suppress` was absent
   from `schema.sql`). A complete baseline migration and query indexes now define
   fresh and existing databases consistently.
8. One already-moderated production row still retained its rate-limit IP hash,
   contrary to the documented retention rule. After the export, that single hash
   was cleared with a narrowly scoped update and a follow-up query confirmed zero
   moderated hashes remain. No submission or map data was changed.

## Reliability and security improvements

- Added a read-only `/api/health` database reachability endpoint.
- Added static security headers, including HSTS, CSP, framing protection,
  permissions restrictions, and no-store/no-index handling for the admin page.
- Added subresource integrity checks for Leaflet, MarkerCluster, and the lazy
  opening-hours bundle.
- Added an independent Overpass fallback, partial-response checks, atomic file
  replacement, plausible-count floors, and shrink protection.
- Kept an explicit, commit-pinned Pages upload after the daily refresh checks;
  repository pushes alone did not trigger a production build during verification.
- Removed automatic geolocation on page load; location is requested only after a
  user action.
- Made the Leaflet location control keyboard-accessible and exposed modals as
  dialogs to assistive technology.
- Moved the admin token from persistent browser storage to tab-only storage,
  added a clear button, and added confirmation for permanent deletion/hiding.
- Removed persistence of optional contributor names in the public form.
- Added Node and Python regression tests, a Worker compilation check, local D1
  migration verification, and a pull-request/main safety workflow.

## Performance observations

The root HTML is large because all map points are embedded in one document
(about 731 KB before compression and about 170 KB over the live Brotli response
at audit time). Marker clustering and deferred opening-hours evaluation keep the
current interface usable, but separating the POI payload from the HTML would make
parsing, caching, and daily deployments more efficient. That is a worthwhile
follow-up, but it should be introduced separately because it changes the site's
core loading path and deserves a staged preview plus rollback plan.

## Operational follow-ups

- Merge only after the Cloudflare preview deployment and safety workflow pass.
- Apply D1 migrations during a planned maintenance window; they add migration
  tracking and indexes but are not required for the current schema to keep serving.
- Consider protecting `main` with required pull-request checks. The daily refresh
  bot currently pushes directly to `main`, so its workflow must be adapted before
  enabling a rule that blocks that push.
- Add Turnstile only if submission abuse appears; the current honeypot, strict
  validation, bounded payload, and salted per-IP rate limit are proportionate to
  present traffic.
